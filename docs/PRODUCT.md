# Aphrodite — 제품 기획과 프로토타입 범위

## 제품의 약속

“30분짜리 구현을 시작하기 전에, 1분 안에 디자인 방향을 함께 확인한다.”

여기서 1분은 앞으로 측정할 경험 목표다. 이미지 생성 시간이나 모델 호출 지연까지 포함해 이미 달성한 지표가 아니다. 저비용의 핵심은 매번 HTML을 새로 생성하지 않고, 이미 검증된 컴포넌트와 토큰을 조합하는 데 있다.

Aphrodite는 코딩 에이전트 앞에 놓이는 시각적 의사결정 작업대다. 사용자는 디자이너처럼 모든 픽셀을 편집하지 않아도 목적, 구성, 브랜드, 이미지 분위기를 결정한다. 에이전트는 사용자가 확인한 컴포넌트 트리와 디자인 계약을 구현의 출발점으로 받는다. 프로토타입은 기대의 일치를 돕지만 최종 제품의 품질을 자동 보증하지는 않는다.

## 이번에 만든 수직 프로토타입

1. 편집 가능한 Form & Field 샘플 프로젝트로 시작한다.
2. 프로젝트 메뉴에서 새 프로젝트를 만들거나 JSON 파일을 연다.
3. Start from a brief에서 이름과 목적을 입력한다. 로컬 규칙이 새 페이지를 구성한다. 기존 페이지는 보존한다.
4. Atelier / Karrot inspired / Toss inspired / Mono 중 하나를 고른다. 모든 페이지가 같은 토큰을 공유한다. 직접 색상·서체 역할·모서리 반경을 바꾸거나 DESIGN.md의 명시적인 색상을 가져올 수 있다.
5. 7종의 블록을 드래그하거나 Add 버튼으로 넣는다. 선택 후 제목·설명·버튼 문구·이미지를 편집하고, 순서 이동·복제·삭제한다.
6. Auto fill은 샘플 카피와 번들 이미지를 넣는다. 기본값은 작성한 내용을 덮어쓰지 않는다. 이미지 업로드·레퍼런스 보관도 가능하다.
7. 데스크톱·375px 모바일·독립 미리보기로 검토한다.
8. Approve direction으로 프로젝트 내용을 확인한다. 편집하면 승인 상태가 해제된다. 승인은 로컬 작업 상태이며 신원 인증이나 변조 방지 서명이 아니다.
9. ZIP으로 PROMPT.md, DESIGN.md, tokens.json, 모든 페이지 HTML, 로컬 에셋, 편집 가능한 프로젝트 JSON을 받는다.

모든 편집은 Undo/Redo가 가능하다. 작업은 해당 웹뷰의 localStorage에 저장된다. 브라우저와 네이티브 앱의 저장 영역은 별개이며 JSON 파일로 이동한다. 저장 공간 오류는 사용자에게 표시한다. 장기 보관은 프로젝트 파일 저장을 사용한다.

## 컴퓨터 유즈를 위한 결정

- canvas 픽셀로만 그리지 않는다. 웹뷰 안에 실제 DOM, button, textarea, select를 둔다.
- 드래그로만 가능한 작업을 만들지 않는다. Add, Move up/down, Duplicate, Delete는 버튼으로도 수행한다.
- 화면에 가능한 다음 행동이 보이고, 완료·오류는 role=status로 표시한다.
- 모달에는 aria-modal, 제목, Escape, 포커스 트랩을 둔다. 배경은 inert 처리한다.
- 에이전트 연결을 가장하는 “Connected” 표시는 넣지 않는다. 외부 에이전트가 동일한 UI를 조작하는 구조다.
- 페이지의 타깃 장치와 에디터 자체의 창 크기를 분리한다. 모바일 미리보기는 375px 컨테이너에서 실제 reflow한다.
- 네이티브 임의 셸 실행이나 광범위 파일 접근 권한을 열지 않는다. 사용자가 고른 저장 경로에만 파일을 쓴다.

## OmD 디자인 하네스로 발전시키기

현재 DESIGN.md 내보내기는 Core v2의 7영역을 참고한 구조적 초안이다. OmD의 Portable Core 인증 또는 Bound System을 주장하지 않는다. 원본 Markdown에서 확인하지 못한 값은 외부 브랜드 사실로 승격하지 않는다. 이번 프리셋의 컴포넌트는 자체 구현이며 공식 SEED/TDS 코드가 아니다.

다음 단계는 `SystemAdapter`가 source DESIGN.md를 검사하고, 후보 그래프를 만들고, 검토 후 채택하는 흐름이다. 채택된 그래프에서 토큰과 component contract를 읽고, 렌더링 및 export가 같은 모델을 소비하도록 한다. 생성 시스템과 프로젝트 결정이 다르면 drift로 표시한다. 스크린샷 검토 결과까지 그래프에 무조건 쓰지 말고 evidence로 보관한다.

화면의 텍스트·이미지·시스템·구성 변경은 승인 상태를 무효화한다. 페이지 전환이나 에디터 확대율 변경은 디자인 변경이 아니다. 이 경계를 후속 그래프 hash binding에도 유지한다.

## 단계별 로드맵

### 1. 실제 사용 루프 검증

이 프로토타입으로 사용자가 3개 이상의 서로 다른 목적을 조립하게 한다. 첫 화면까지 걸린 시간, 방향 수정 횟수, export 이후 디자인 재작업을 측정한다. 외부 Astra/Codex 컴퓨터 유즈로 동일 시나리오를 실행하고 버튼 이름·포커스·업로드·다운로드 실패를 분류한다.

### 2. OmD 계약 연결

전체 색상 파서 대신 OmD validator와 adapter를 연결한다. 주력 디자인 시스템 2개에서 실제 anatomy/state/slot을 이식한다. 기존 프리셋 데이터와 공식 브랜드 구현을 명확히 구분한다. 실제 화면과 export의 시각 회귀 검사를 추가한다.

### 3. 이미지 → 컴포넌트 후보

사용자의 레퍼런스 또는 생성 이미지에서 레이아웃 영역·내용 역할·밀도·스타일 힌트를 추출한다. 모델 출력은 임의 코드가 아닌 버전이 있는 `SceneCandidate` JSON으로 받는다. 허용된 컴포넌트와 슬롯에만 매핑하고, 적합도가 낮은 영역은 사용자 선택으로 남긴다. 컴퓨터 유즈 에이전트가 조립한 뒤 실제 스크린샷으로 차이를 확인한다.

### 4. 생성 및 배포 통합

이미지·영상·Blender는 provider adapter로 분리한다. 첫 요청 전에 비용·해상도·취소·재시도 범위를 보여준다. 인증 토큰은 시스템 키체인에 보관한다. Codex 계정 세션을 추출하거나 비공식 OAuth 경로를 가정하지 않는다. 지원되는 공식 연결 방식이 확인된 뒤 구현한다.

플러그인은 사용자 의도 → Aphrodite 열기 → 사용자 검토 → 내보낸 경로 받기 → 구현의 얇은 연결층으로 만든다. 독립적인 거대한 생성 런타임을 다시 만들지 않는다.
