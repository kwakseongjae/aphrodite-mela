# Aphrodite: 공유하고 싶어지는 순간과 기업이 관심 가질 이유

작성일: 2026-09-08. 현재 앱을 직접 조작한 관찰과 공개된 Figma 자료를 구분해 정리한다. 바이럴이나 투자·인수 가능성을 예측한 문서가 아니다. 아래의 우선순위와 목표 수치는 검증할 제품 가설이다.

## 지금의 판단

현재 버전은 작동하는 디자인 작업대다. 다만 대표 데모가 가구 랜딩 한 종류이고 Auto fill이 고정 콘텐츠여서, 아직 “내 문제를 풀어주는 도구”라는 증거는 약하다. 예쁜 첫 화면은 관심을 끌 수 있지만, 반복 사용과 기업의 전략적 관심을 설명하려면 디자인 결정이 실제 코드까지 유지되는 결과를 보여줘야 한다.

가장 유망한 포지셔닝 가설은 **“에이전트가 구현하기 전에 사람이 디자인 방향을 확정하고, 그 결정이 구현까지 유지되는 디자인 하네스”**다. 시간 절약뿐 아니라 잘못된 방향의 장시간 구현을 줄이는 것이 가치다.

## 실제 조작에서 확인한 점

| 관찰 | 의미 | 다음 작업 |
| --- | --- | --- |
| Brief 입력 뒤 새 페이지가 바로 조립된다 | 초안 접근이 쉽다 | SaaS·커머스·콘텐츠의 구조가 확연히 달라지게 만들기 |
| 빈 이미지 영역이 Auto fill 한 번으로 채워진다 | 전후 변화가 영상에서 이해되기 쉽다 | 사용자 도메인별 카피·에셋과 사용자 이미지 매핑 |
| Atelier → Toss로 컬러·서체·반경이 바뀐다 | 브랜드 전환의 개념은 전달된다 | 정보 밀도·타이포 스케일·컴포넌트 anatomy·상태까지 바뀌어야 함 |
| 모바일은 실제로 세로 재배치된다 | 결과를 손으로 검토할 수 있다 | 데스크톱/모바일 동시 비교와 페이지 전체 보기 |

| Export는 긴 프롬프트를 보여준다 | 정보는 전달되지만 마지막 시각적 보상이 약하다 | 승인 화면과 구현 화면의 나란한 비교 |
| 키보드와 접근성 이름으로 실제 앱을 조작할 수 있다 | 컴퓨터 유즈 친화성의 시작점이다 | 고정 과제 반복 실행·복구·성공률·작업시간 측정 |
| 이미지→컴포넌트 자동 매핑이 없다 | 사용자가 말한 핵심 자동화는 아직 증명되지 않았다 | 다른 UI 확장보다 이 연결을 먼저 검증 |

## 바이럴에 필요한 포인트

### 즉시 이해되는 변화

공유용 메시지 가설: **“코딩을 기다리기 전에, 만들 화면부터 결정하세요.”**

대표 데모는 한 문제를 끝까지 보여줘야 한다. “레퍼런스 한 장 → 실제 시스템 컴포넌트로 조립 → 내용 채우기 → 세 가지 방향 비교 → 선택한 모습대로 구현”이 좋은 후보이다. 현재는 앞의 자동 매핑과 마지막 실제 구현 비교가 없으므로 완성된 기능처럼 홍보하면 안 된다.

30초 데모 구성안은 목표이며 현재 소요시간 측정값이 아니다:

1. 0–5초: 사용자가 원하는 화면과 레퍼런스를 보여준다.
2. 5–12초: 이미지가 편집 가능한 컴포넌트로 대응되는 과정을 보여준다.
3. 12–20초: 동일 목적의 세 가지 방향을 나란히 비교하고 하나를 고른다.
4. 20–30초: 실제 코드 실행 결과가 선택한 방향을 유지함을 보여준다.

긴 생성 구간을 편집으로 없앤 경우에는 표시해야 한다. “1분”, “거의 무료”는 전체 흐름·하드웨어·모델·캐시·네트워크·비용 범위를 정한 실측 뒤에 사용한다.

### 보는 사람이 직접 참여할 이유

방향 A/B/C 투표, 한 번의 리믹스, 사용자 소유 브랜드 적용이 자연스러운 참여 지점이다. 공유물이 원본 프로젝트와 시스템을 보존해야 리믹스가 재사용으로 이어진다. 공개 공유는 별도 사용자 동의를 거치고 private 프로젝트를 자동 게시하지 않는다.

### 반복해서 다른 결과

기업 이름을 바꿔도 같은 랜딩이 나오는 데모는 쉽게 소진된다. 3개 도메인 × 3개 시스템 × 2개 화면에서 “다른 목적, 같은 브랜드 일관성”을 먼저 보여주는 것이 좋다. 카탈로그 숫자를 늘리기보다 좁은 범위에서 높은 완성도를 확보한다.

## Figma 같은 기업에 의미 있을 포인트

Figma의 공식 MCP 문서는 이미 네이티브 캔버스 작성, 디자인 변수·컴포넌트·레이아웃 전달, Make 리소스, 실제 코드 컴포넌트 재사용을 설명한다. 따라서 MCP 연결, 프롬프트 export, 에이전트로 캔버스 조작 그 자체만으로는 충분한 차별화가 어렵다는 것이 내 판단이다. [공식 MCP 문서](https://developers.figma.com/docs/figma-mcp-server/), [Code Connect 통합 문서](https://developers.figma.com/docs/figma-mcp-server/code-connect-integration/).

Figma는 Weavy 인수 발표에서 생성 결과를 분기·리믹스·정교하게 편집하는 제어력과 창작 커뮤니티를 강조했다. 이 사례에서 “전문적으로 통제 가능한 워크플로와 실제 사용하는 커뮤니티가 중요하다”는 힌트를 얻을 수 있지만, 이것을 Aphrodite에 대한 인수 의향이나 보편적인 인수 기준으로 해석할 수는 없다. [Figma의 Weavy 발표](https://www.figma.com/blog/welcome-weavy-to-figma/).

기업 관심을 설득할 근거는 다음과 같다. 이는 공개된 구매 조건이 아니라 제품 가설이다.

| 포인트 | 보여줘야 할 증거 | 현재 격차 |
| --- | --- | --- |
| 실제 DS 재사용 | 기존 React 컴포넌트와 variant/slot/token의 정확한 연결 | 현재는 자체 HTML과 일부 색상 프리셋 |
| 디자인 의도 보존 | 승인 화면 대비 구현 화면의 차이, 토큰 이탈, 수정 횟수 | 승인 무효화는 있으나 구현 검증 루프 없음 |
| 에이전트 실행 신뢰성 | 여러 모델·도구에서 같은 과제의 성공률·실패 복구·시간 | 일부 UI 조작 확인, end-to-end 반복 벤치 없음 |
| 기존 디자인 생태계 연결 | Figma component ID / Code Connect / 사용자 코드 라이브러리 연계 | 아직 연동 없음 |
| 반복 채택 | 자신의 브랜드를 가져오고 두 번째·세 번째 작업에도 사용하는 팀 | 사용자 코호트 데이터 없음 |
| 축적되는 차별성 | 고품질 컴포넌트 계약·variant 매핑·검증 규칙·사용자 허용 평가셋 | 작은 자체 레지스트리부터 시작 |

컴퓨터 유즈는 핵심 사용 경험이자 검증 대상으로 유지한다. 다만 “오직 픽셀 클릭으로만 작동한다”를 차별점으로 삼을 필요는 없다. 장기적으로 같은 명령 모델을 UI와 구조화된 연결이 함께 쓰면 자동화의 지연과 오류를 줄일 여지가 있다. 이는 후속 아키텍처 제안이지 현재 구현을 바꾼 것은 아니다.

## 다음 개발 순서 제안

1. **참조 화면 → 실제 컴포넌트 조립**을 한 도메인·한 시스템에서 끝까지 구현한다. 결과가 기존 라이브러리의 어느 컴포넌트와 연결되는지 보이게 한다.
2. **방향 세 가지 나란히 비교**와 원클릭 리믹스를 추가한다. 색상만 바꾸지 않고 구조·정보 밀도·타입 스케일까지 비교한다.
3. **승인 → 실행 코드 → 시각 검증**을 연결한다. 사용자 수정이 필요한 차이를 보여주고 반복해서 줄인다.
4. **실제 사용자 5팀을 대상으로 탐색**한다. 이 숫자는 시작용 표본이며 시장 검증에 충분하다는 뜻은 아니다. 각 팀이 자기 시스템으로 반복 작업하는지 관찰한다.
5. 실측 결과와 작동하는 데모가 쌓인 뒤 플러그인·공유 경로를 확장한다. 인증·모델 추가를 첫 번째 성과로 삼지 않는다.

## 측정 계획

- 첫 검토 가능 화면까지의 시간: brief 제출부터 사용자가 판단 가능한 화면까지, p50/p95와 실패를 함께 보고한다.
- 에이전트 흐름 성공률: 동일하게 정의한 과제를 수동 개입 없이 완료한 비율. 모델·버전·횟수·실패 사유를 함께 남긴다.
- 구현 후 재작업: 동일 brief의 기존 방식과 비교한 수정 횟수·시간. 사용자 숙련도와 작업 순서를 통제한다.
- 시스템 일치: 색상뿐 아니라 컴포넌트 identity, variant, spacing, 상태 준수 항목을 검사한다.
- 반복 사용: 첫 export 뒤 실제 두 번째 프로젝트에서 다시 사용했는지 본다. 조회수·별 개수와 분리한다.
- 공유 전환: 공유 화면 조회 → 리믹스 시작 → 자신의 작업 export를 구분한다.

첫 목표는 “완성품 품질 보장”이 아니라 **방향이 어긋난 구현을 얼마나 줄이는지 입증하는 것**이다. 현재 스크린샷은 사용성 프로토타입의 증거이며, 이 효과나 수요를 이미 입증한 자료는 아니다.
