# 카탈로그를 어디로 넓힐 것인가 — 근거

작성 2026-09-15. "DESIGN.md가 400개가 넘는데 종류마다 최소 10개는 있어야 하지 않나"에 대한 답. 세어보고 답한다.

## 먼저, 400개는 변형의 근거가 아니다

`design-md/`의 440개는 400개 브랜드의 **토큰과 규칙**이지 레이아웃 변형 400가지가 아니다. 그 400개를 실제로 쓰는 일은 D1~D4에서 했다 — 토스를 가져오면 토스의 회색과 빨강이 **같은 변형에** 들어가 다르게 보이는 것. 400개는 **토큰의 근거**였다.

변형의 근거는 따로 세야 한다. 그래서 세었다.

## 코퍼스가 문서화하는 컴포넌트 — 헤딩 2,084개

440개 파일 전부에 §4가 있고, 파일당 컴포넌트 헤딩이 중앙값 5개다. 헤딩의 마지막 명사를 세면:

| 명사 | 횟수 | 우리 상태 |
|---|---:|---|
| button / action | 394 | ✅ |
| container / card | 297 | ✅ |
| navigation / bar | 224 | ✅ |
| input / form | 226 | ✅ |
| badge / tag / chip | 209 | ✅ |
| tab | 86 | ✅ |
| dialog · toggle · toast · footer | 각 23–29 | ✅ |
| link | 15 | ❌ |

**상위 카테고리가 전부 우리가 이미 가진 것이다.** 빠진 종류를 찾으러 갔다가 종류는 다 있다는 걸 확인했다.

## 상태(state)를 좇는 것은 값이 낮다

버튼 섹션 407개에서 상태 표현을 뽑으면 가장 흔한 것들이 이렇다.

```
default only           15
pressed                15
focus                   8
no interaction event    6
pseudo-state captured   6
no hover                4
default capture only    3
```

**"default only"·"no interaction event"·"default capture only"** 이 실제 브랜드 문서의 흔한 답이다. 살아 있는 사이트에서 관찰해 기록했기 때문에 기본 상태만 잡힌 것이다. 즉 **상태를 늘리는 데는 코퍼스가 근거를 주지 않는다.**

## 우리 카탈로그의 실제 숫자

35종 · 변형 108개(종당 중앙값 3) · 상태 83개 · **조합 990개**.

그런데 평균이 진실을 가린다. 쪼개보면 둘로 갈린다.

| | 변형 | 상태 | 프로바이더 | 조합 |
|---|---:|---:|---:|---:|
| 컨트롤 (button·input·cards·table·notice·badge…) | 3–4 | 3–4 | 5 | **45–64** |
| 페이지 섹션 (hero·features·products·cta·footer·nav) | 3–4 | **1** | **1** | **3–4** |
| Moa 레시피 | 1 | 1 | 1 | 1 |

**컨트롤은 이미 종당 45~64개다. 얇은 것은 페이지 섹션이다.** 그리고 랜딩 페이지의 성격은 버튼의 상태가 아니라 섹션의 레이아웃에서 나온다.

## 그래서 제안

**섹션 변형을 3~4개에서 8~10개로.** 7종(navigation·hero·features·products·testimonial·cta·footer) × 5개 추가 ≈ 35개. 조합으로는 990 → 1,300 남짓이지만, **사람이 느끼는 다양성은 여기서 나온다.**

상태와 프로바이더는 늘리지 않는다. 코퍼스가 근거를 주지 않고, 섹션에 상태라는 개념이 잘 맞지도 않는다.

## 먼저 게이트

오늘 23개 섹션 변형을 한 페이지에 깔고 390px로 렌더해 보니 **그중 둘이 읽을 수 없는 상태**였다 — 배너 CTA의 버튼 글자, 플레이스홀더 위의 캡션. 둘 다 "한 표면을 위해 고른 색을 다른 표면에 쓴" 같은 실수다.

**변형 하나는 공짜가 아니다.** 3배로 늘리면 그런 것도 3배가 된다. 그래서 순서는:

1. **게이트** — 새 변형은 CSS 불변식(흰 글자는 어디 놓이는지 말해야 한다, 버튼 면을 칠하면 글자도 말해야 한다)과 **390px 렌더 육안 확인**을 통과해야 들어온다. 앞의 둘은 이미 테스트로 있다.
2. **확장** — 게이트가 있으면 워커에게 병렬로 맡길 수 있다.

## 첫 확장 — hero 4 → 9 (완료 2026-09-15)

게이트가 실제로 작동하는지 보려고 hero부터 했다. 마크업은 그대로, **레이아웃만 CSS로** 추가한다 — 사람이 변형을 바꿔도 쓴 글이 날아가지 않는다.

| 변형 | 구성 |
|---|---|
| `full-bleed` | 사진이 전체를 채우고 카피가 그 위에. 스크림을 깔아 사진이든 플레이스홀더든 읽힌다. |
| `centered` | 사진 없이 가운데. 첫인상이 문장인 브랜드용. |
| `offset` | 카피 카드가 사진 모서리를 밟고 선다. |
| `duo` | 카피 아래 두 칸. |
| `quiet` | 한 줄과 밑줄 링크. 버튼도 사진도 없다. |

**게이트가 세 번 일했다.**

1. `offset`의 겹침이 안 일어났다 — 카피가 마크업에서 먼저라 음수 여백이 위쪽 허공을 당겼다. **사진을 올려 붙이는** 쪽으로 뒤집었다.
2. `duo`의 두 번째 칸이 **밋밋한 회색**이라 실수처럼 보였다. 빈 이미지 칸과 같은 해치로 칠해 짝으로 읽히게 했다.
3. 390px에서 `duo`의 두 칸이 **납작해졌다** — 컨테이너의 min-height를 두 줄이 나눠 가졌다. 칸마다 높이를 줬다.

셋 다 데스크톱 렌더나 폰 렌더를 **눈으로 보고** 찾았다. CSS 테스트로는 하나도 안 잡혔을 것들이다. 그래서 게이트는 테스트 + 두 폭의 렌더 확인 둘 다여야 한다.

테스트도 늘렸다. 이제 **사진 위에 카피를 올리는 변형은 스스로 카피 색과 스크림을 선언해야** 하고, **고를 수 있는 변형은 전부 스타일이 실재해야** 한다.

## 참고: 섹션에는 프로바이더가 없다

컨트롤은 MUI·shadcn·SEED·Astryx 어댑터가 있어 조합이 5배가 된다. 섹션은 전부 우리 것이다. 이건 결함이 아니라 사실이다 — 어떤 라이브러리도 "에디토리얼 히어로"를 주지 않는다. 섹션의 다양성은 우리가 직접 만드는 수밖에 없다.

## 두 번째 확장 — 일곱 종 전부 8~9개 (완료 2026-09-16)

hero에 이어 나머지 여섯 종에 다섯 개씩 넣었다. 마크업은 그대로, **레이아웃만 CSS로**.

| 종 | 추가한 변형 |
|---|---|
| navigation | `stacked` `bordered` `brand` `wide` `quiet` |
| features | `grid` `index` `statement` `stack` `plain` |
| products | `rows` `rail` `lookbook` `feature-first` `panels` |
| testimonial | `pull` `brand` `aside` `plate` `bare` |
| cta | `centered` `dark` `rule` `panel` `card` |
| footer | `stacked` `centered` `brand` `tall` `rule` |

**섹션 변형 23 → 58.** 카탈로그 전체로는 35종 · 변형 143개 · 상태 83개 · **조합 1,025개**.

조합이 990에서 1,025로만 는 것은 예상대로다 — 섹션은 상태도 프로바이더도 1이라 변형 하나가 조합 하나다. 위에서 "1,300 남짓"이라고 적었던 건 틀렸다. 늘어난 것은 조합 수가 아니라 **사람이 고를 수 있는 레이아웃**이고, 그게 애초에 목적이었다.

### 게이트를 앱 밖으로 꺼냈다

첫 확장 때는 앱을 띄워 놓고 렌더를 받아 눈으로 봤다. 이번에는 그게 막혔다. **연결 모드는 세션 한정이라 JS 모듈을 하나 고칠 때마다 HMR이 화면을 새로 그리고 연결이 풀린다.** CSS 한 줄 고치고 렌더 한 번 받는 일을 예순 번 하려면 사람이 예순 번 「허용」을 눌러야 한다. 그건 게이트가 아니라 고문이다.

그래서 `scripts/variant-gate.mjs`를 만들었다. 같은 `page.css`, 같은 렌더러, 헤드리스 크롬.

```sh
node scripts/variant-gate.mjs                  # 일곱 종 × 두 폭 = 14장
node scripts/variant-gate.mjs products cta     # 종만 골라서
GATE_FRAME=390 node scripts/variant-gate.mjs   # 폰 폭 밖으로 삐져나온 게 있는지
```

세 가지를 배웠다.

1. **`makeBlock(kind)`는 항목이 하나뿐이다.** 그걸로 찍으면 다열 변형을 판단할 수 없다. `makeBlock(kind,true)`로 실제 카피와 실제 개수를 넣어야 한다.
2. **`file://`은 `/assets/`를 못 찾는다.** 이미지가 alt 텍스트로 쪼그라들어 비율이 전부 거짓이 된다. 실제 파일 경로로 바꿔야 한다.
3. **높은 헤드리스 창은 요청한 폭으로 레이아웃하지 않는다.** `--window-size=390,12000`으로 찍은 폰 샷이 실제로는 490px쯤에서 배치돼 있었고, `.design-page{overflow:hidden}`이 넘친 부분을 잘라내 **멀쩡해 보였다.** 지금은 창을 믿지 않고 `main.design-page{width:390px}`로 컨테이너를 CSS에서 직접 붙잡는다.

3번이 특히 무섭다. **거짓 통과를 주는 하네스**는 게이트가 없는 것보다 나쁘다.

### 게이트가 잡은 것

여덟 개다. 전부 **렌더를 보고** 찾았고, CSS 테스트로는 하나도 안 잡혔을 것들이다.

| 무엇 | 원인 |
|---|---|
| `cta`에 `split`이 두 번 | 새 변형 이름을 `halves`에서 바꾸다 기존 변형과 충돌. 피커에 같은 단어가 둘 |
| `features·index` `stack`, `products·list` `rows`, `features·numbered`에서 제목과 문장이 벌어짐 | `gap`은 **행에도** 걸린다. 열 간격을 주려고 쓴 값이 제목과 문장을 갈라놨다 |
| `products·rows` `list`의 카피가 사진 높이만큼 늘어짐 | 행을 걸치는 사진이 그 행들의 높이를 정한다. 행에 이름을 주고 남는 공간을 빈 행으로 보냈다 |
| `testimonial·aside`의 인용부호가 라벨 위에 | 부호와 본문이 **똑같이 8%**에서 시작했다 |
| `features·plain`이 폰에서 제목이 한 줄에 한 단어 | 공용 모바일 스택이 문장을 2열에 놓는데 `plain`에는 2열이 없다 |
| `products`의 칸이 사진의 원본 너비만큼 벌어짐 | 그리드 칸의 최소 너비는 안에 든 이미지의 고유 너비다. `min-width:0` |
| `features·grid`의 세 번째 카드가 혼자 남음 | 2열에 홀수. 마지막 하나가 줄을 다 쓰게 했다 |
| `cta·halves`라는 이름이 79:21을 가리킴 | 이름이 계약이다. `panel`로 바꿨다 |

### 테스트로 남긴 것

이름 충돌은 **눈이 아니라 테스트가 잡아야 했다.** 그래서 넣었다 — 일곱 종 전부에 대해 **고를 수 있는 변형은 한 번만 이름을 갖고, 전부 실재하는 스타일이 있어야 한다.** 중복 id가 한 번 통과한 적이 있으니 다시는 못 통과한다.

나머지 일곱은 여전히 눈으로 찾은 것들이다. 그게 이 게이트의 존재 이유다 — **두 폭의 렌더를 사람이 보는 단계는 빠지지 않는다.**


## 세 번째 확장 — 앱 레시피에 변형을 준다 (2026-09-16)

지금까지 앱 화면은 **한 모양뿐이었다.** `moaSpecs`의 네 레시피(`moasidebar`·`moatoolbar`·`moacard`·`moadetail`)가 각각 변형 하나씩이라, 앱을 만들려면 우리가 만든 그 데모 그대로 써야 했다. **하나는 데모지 어휘가 아니다.**

마크업은 그대로, 레이아웃만 CSS로 — 섹션 확장과 같은 규칙이다.

| 레시피 | 추가한 변형 |
|---|---|
| moasidebar | `rail` `grouped` `quiet` |
| moatoolbar | `stacked` `dense` `split` |
| moacard | `compact` `cover` `bare` |
| moadetail | `sheet` `plain` |

**4 → 15.** 가드 테스트도 섹션과 같은 것으로 늘렸다 — 고를 수 있는 앱 변형은 전부 실재하는 스타일이 있어야 한다.

### 게이트를 먼저 고쳐야 했다

처음 렌더는 **전부 똑같아 보였다.** 카드를 레인 밖 페이지에 깔면 전체 너비로 늘어나서 `compact`든 `bare`든 차이가 안 보인다. **판단할 수 없는 샷을 통과시키는 하네스는 게이트가 아니다.** 그래서 앱 레시피는 변형마다 **진짜 워크스페이스 셸 안에** 넣어 렌더하도록 게이트를 고쳤다.

고치고 나니 바로 하나 잡혔다. `rail`을 68px 아이콘 전용으로 설계했는데, **라벨이 글리프와 같은 텍스트 노드에 있어 CSS로 쪼갤 수 없다.** 68px에서는 모든 라벨이 한 음절씩 세로로 쌓여 읽을 수가 없었다. 읽을 수 없는 변형은 변형이 아니라서, `rail`은 **글자가 한 줄에 들어가는 가장 좁은 폭(152px)** 으로 바꾸고 넘치면 말줄임으로 잘랐다.

### 확인한 것과 확인 못 한 것

- **1440에서 넷 다 눈으로 확인했다.** `default`와 구분되고, 셸 안에서 제 역할을 한다.
- **390은 못 했다.** 앱 셸에는 1100px 아래로 내려가는 브레이크포인트가 없어서 폰 폭에서 사이드바와 상세 패널이 옆으로 넘친다. **이건 원래 그랬던 것이고 이번에 고치지 않았다.** 한 번 고쳐 봤다가 사이드바가 사라지고 보드는 그대로여서, **동작을 이해하지 못한 CSS를 싣느니 빼는 쪽**을 골랐다. 5레인 보드를 폰에서 어떻게 할지는 스타일시트가 혼자 정할 문제가 아니다.
- ~~**게이트의 390 검사는 미디어 쿼리를 못 건다**~~ — **고쳤다(09-17).** 컨테이너를 CSS로 붙잡던 이유는 "높은 헤드리스 창이 요청한 폭으로 레이아웃하지 않는다"는 과거 관측이었는데, **지금은 사실이 아니다** — 300·3000·12000 픽셀 높이에서 전부 390으로 레이아웃하고 `@media`가 걸린다. 폰 샷은 이제 진짜 390 창에서 찍는다.

  옛 방식에는 구멍이 있었다: 뷰포트가 넓은 채라 **스타일시트의 폰 브레이크포인트가 통째로 검사되지 않았다.** 앱 셸 폰 레이아웃에 저녁 하나를 쓴 것이 이것 때문이다.

  `GATE_FRAME`은 일부러 옛 방식을 남겼다 — 프레임 **밖으로** 삐져나온 것을 보려면 옆에 캔버스가 있어야 하는데 진짜 390 창에는 그게 없다. 그 샷은 실행할 때 "여기선 @media가 안 걸린다"고 스스로 말한다.
